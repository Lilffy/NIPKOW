# 两个 AI 通过 GitHub 协作的约定（v1）

> 适用对象：A 的 DeepSeek / B 的 DeepSeek（以及两位人类）
> 目标：**所有工作痕迹可追溯、不互相踩文件、不需要私聊也能推进**
> 仓库：`https://github.com/Lilffy/NIPKOW`（Private）

---

## 0. 三条铁律

1. **只走 GitHub**：结论、交接、提问、验收全部沉淀成 Issue / PR / Commit。
   微信里说的"我改好了"不算；没有 issue 或 PR 记录的事等于没发生。
2. **只改自己的地盘**（见 §2 文件所有权）。要动别人的文件，先开 issue 征求同意。
3. **一个 Issue 一件事**，一个 PR 一个主题。不要把三件事塞进一个 PR。

---

## 1. 三种通道，各管什么

| 通道 | 用途 | 谁写 | 例子 |
|---|---|---|---|
| **Issue** | 提需求、报 bug、问问题、交接、状态广播 | 双方 | "A：J3 焊盘间距确认" |
| **PR** | 交付代码/文档，请求对方审阅 | 改代码的一方 | "feat(sw): M1 红外 EXTI" |
| **Commit** | 记录实际改动 | 改代码的一方 | `fix(sw): PB2 极性` |

**评论 (@mention)**：需要对方回应时，在 issue/PR 里 `@Lilffy`（B）或 `@Layla82693`（A）。

## 3. Issue 规范

### 3.1 标题格式

```
[A] 硬件：J3 焊盘间距确认
[B] 固件：M1 红外 EXTI 实现
[BUG] 上电后 5V 只有 3.2V
[Q] 鼓的 16 孔角度怎么标定？
```

### 3.2 必备字段（写在正文里，AI 可解析）

```markdown
**Owner:** A
**Type:** hw | sw | docs | bug | question
**Priority:** P0 | P1 | P2
**Depends-on:** #12（没有就写 none）
**Blocked-by:** #15（没有就写 none）
**Status:** todo | doing | blocked | review | done
**Acceptance:** 一句话可验证的验收标准
```

> 状态同时用 label 标（`status:*`）。**字段与 label 不一致时以 label 为准**。

### 3.3 生命周期

```
todo → doing → review → done
         ↓
      blocked（写明卡在谁/什么）
```

- 开始做：加 `status:doing` 并回一条评论「开始，预计 X」
- 卡住：加 `status:blocked`，正文写清**卡在谁**（A / B / 人类 / 物料 / 网络）
- 等对方看：加 `status:review`，@对方
- 完成：附**验收证据**（见 §6）再关；关闭时写「已完成：<commit hash / 测试数据>」

### 3.4 issue 里不要做的事

- 不要一条 issue 里塞多个任务（拆 issue）
- 不要在 issue 里贴超长日志（贴关键行 + 附件链接）
- 不要把 token/密码/个人信息写进去

## 4. PR 规范

### 4.1 什么时候开 PR

- **跨边界改动**（改了别人 owned 的文件）→ 必须 PR + 对方 review
- **自有的重要改动**（固件新模块、硬件文件替换）→ PR，方便对方知道
- 改错别字/README → 可以直接 push main

### 4.2 格式

标题：`type(scope): 摘要`，例如 `feat(sw): M1 红外 EXTI + 消抖 + 1s LED`

正文必须包含：

```markdown
## 改了什么
- ...
## 为什么
- ...
## 怎么验证
1. 命令 / 步骤
2. 预期结果
## 影响的 issue
Closes #12
## 风险 / 需要注意
- ...
```

### 4.3 规则

- 一个 PR 只做一件事，**改动 < 400 行**（大改拆 PR）
- **不要自己合并别人的 PR**；作者本人可以合并自己的（已 review 通过的）
- 不 force push `main`
- PR 里要附编译/测试结果（哪怕只是"本地编译通过"）

## 5. 每日状态广播（双方必做）

固定 issue：**「📌 每日状态」**（编号见仓库，由 B 创建并保持 open）

每天工作结束前，各发一条评论：

```
## 2026-10-25 A
- 做了：电源区焊接完成，3V3=3.29V / 5V=4.98V / U3 42°C
- 下一步：焊 RGB 区
- 阻塞：无
- 需要 B：确认 J4/J5 极性（见 #12）
```

B 同理。**这比私聊可靠，AI 每天开工先读这条 issue 的最新评论。**

---

## 6. 验收证据标准（关 issue 的门槛）

| 类型 | 必须附 |
|---|---|
| 硬件焊接 | 万用表读数（电压/阻值）+ 板子照片（含日期） |
| 硬件测试 | 波形截图（示波器/逻辑分析仪）或串口日志 |
| 固件功能 | 编译输出（size）+ 串口打印 + 现象描述 |
| 文档 | 文件路径 + 对应源码/截图 |

没证据的 issue 不要关；证据不足就补，别写"应该没问题"。

---

## 7. 冲突处理

1. 两个人改了同一文件 → 后提交的一方负责 rebase 并保留双方意图
2. 语义冲突（同一个引脚两种定义）→ 开 `[Q]` issue，**人类裁决**，不要自行改
3. 代码合并冲突 → `git pull --rebase`，解决后 `git push --force-with-lease` 到**自己的分支**
4. 测试结果矛盾 → 各自附证据，人类裁决

## 7.5 推送闭环协议（每次 push 必做）

> 目的：对方不看聊天记录、只读 GitHub 也能知道"你刚推了什么、我上次推到哪"。

### 推送前（必做，防止覆盖对方成果）

1. `git pull --rebase`（先同步）
2. **读对方最近一次记录**：
   - issue **#18 每日状态** 最近 3 条评论
   - `git log --oneline -5`（看对方最近 commit）
   - 有未读的 `[A]` / `[B]` issue → 先处理
3. 确认没有未合并的冲突再修改文件

### 推送后（必做，固定格式评论进 #18）

```markdown
## 推送记录 YYYY-MM-DD HH:MM [A|B]
- commit: <hash> <一句话>
- 改了哪些文件: 
- 验证: <编译 size / 串口日志 / 测试结果>
- 影响对方: <需要对方注意什么，或 none>
- 下一步: 
```

**规则**：

- 每次 `git push` 之后 **10 分钟内**必须发这条评论（同一 commit 多次 push 可合并成一条）
- 只写"完成了"不算，必须写**验证结果**
- 对方看到后若需要跟进，在同一 issue 回复或开新 issue
- 24 小时内无回应 → 在 issue @对方，仍无 → 升级人类（§8）

### 判断"对方更新了没有"

- `git log --oneline` 顶部出现自己没见过的 commit
- #18 出现新的"推送记录"评论
- 有新的 open issue 且 `Owner` 不是自己

## 8. 什么时候必须升级给人类

以下情况**停下，开 issue 并 @两位人类**：

- 要改原理图 / PCB / BOM（板已冻结）
- 涉及上电、电机旋转、高温、短路风险
- 预算、采购、下单
- 赛题理解有歧义
- 连续 2 次测试结果不一致
- 对方 24 小时没响应（网络/考试）

---

## 9. 网络受限时

- `git commit` 不需要网络；先提交到本地，网络恢复再 push
- push 失败不要反复重试；在「每日状态」issue 留一句"网络问题，已本地提交待推"
- 不要因为网络问题手动改远端文件（会丢历史）

---

## 10. 安全

- 不提交：token、密码、私钥、身份证/学号、宿舍门牌、人脸照片
- 仓库已设为 **Private**
- 赛题/核心板资料可以传；测试照片只拍板子和波形

---

## 11. 每次开工/收工的 checklist

**开工**
- [ ] `git pull --rebase`
- [ ] 读「📌 每日状态」最新评论
- [ ] 认领/创建 issue，加 `status:doing`

**收工**
- [ ] `git add -A && git commit -m "type(scope): ..."` && push
- [ ] 在对应 issue 评论进度 + 证据
- [ ] 在「每日状态」写今日总结
- [ ] 有阻塞 → 开 `[Q]` issue 或标 `status:blocked`
